# Functions

Project functions are JavaScript modules deployed through the control API and
invoked at `/functions/v1/:projectId/:slug`. They run in the **functions
runtime** (`platform/workers/functions-runtime`), a separate container.

```js
export default async function (req) {
  // req: method, path, query, headers, body, json(), text(), env
  const r = await fetch(`${req.env.ODB_REST_URL}/orders?select=*`, {
    headers: { apikey: req.env.SERVICE_KEY },   // a project secret
  });
  return { status: 200, body: await r.json() };  // or a Response
}
```

## Isolation

| Layer | What it does |
|---|---|
| Container | `functions-runtime` is not on the platform network. It has no route to Postgres, Redis, PgBouncer or the internal services. Read-only root filesystem, all capabilities dropped except those listed below, `no-new-privileges`, and limits of 512 processes, 2 GB memory and 2 CPUs (`FUNCTIONS_MEMORY_LIMIT`, `FUNCTIONS_CPUS`). |
| Networks | `functions_rpc` is internal and has no route out. Only api-service and the runtime are on it. `functions_egress` connects the runtime to the internet and to the gateway (Caddy, alias `gateway`). |
| Firewall | Function processes (uids 20000–29999) may reach Docker DNS, the gateway on port 80, and public addresses. Private, loopback, link-local (cloud metadata), CGNAT and multicast ranges are rejected, and so is all IPv6. The rules are set before the runtime starts, and `NET_ADMIN` is removed from its capability bounding set. |
| Process | One Node 22 process per invocation, running as a uid derived from the project ID, so projects cannot signal or inspect each other's processes. |
| Node permission model | A function may read only the runner and its own code file (owner-only, mode 0400, in a directory it cannot list). It cannot write files, spawn processes, start worker threads or load native addons. |
| Limits | `memory_mb` caps the V8 heap: a function that runs out gets a 500 "Function ran out of memory". `timeout_ms` is enforced with SIGKILL. Output is capped at about 6 MB, and `FUNCTIONS_MAX_CONCURRENCY` limits concurrent invocations (503 when busy). |
| Environment | Only `PATH`, `NODE_ENV`, `TZ` and `HOME` are set on the process. Project secrets and `ODB_*` URLs are passed as `req.env`, never as process environment. |

api-service authenticates to the runtime with `FUNCTIONS_RUNTIME_TOKEN`, a
shared secret generated by `make generate-secrets`.

The remaining trust boundary is the Linux kernel shared with the host. Treat
this as container isolation, not a VM. For hostile multi-tenant code, run the
runtime under gVisor (`runtime: runsc`) or on a separate host.

## Calling the platform from a function

`req.env` contains `ODB_URL`, `ODB_REST_URL`, `ODB_AUTH_URL`,
`ODB_STORAGE_URL` and `ODB_FUNCTIONS_URL`. These point at the internal gateway
(`http://gateway`), the only internal address a function may reach.
`ODB_PUBLIC_URL` is the external URL, for links shown to users. Calls through
the gateway are authenticated like any other client, with an API key or a user
token.

The gateway alias needs Caddy to serve plain HTTP on `:80` for any host. That
is how `infrastructure/caddy/Caddyfile` is set up. If you replace it with a
domain-only site block, add an `http://gateway` site with the same routes.
